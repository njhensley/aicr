Module 1

Why AICR & the four-stage model

Running GPU-accelerated Kubernetes reliably is hard because small version differences cause expensive-to-reproduce failures. AICR turns the known-good combinations into a reproducible, verifiable artifact.

01 · Framing

A configuration generator — and what it is not

AICR is…

A generator of validated, version-locked config artifacts (Helm values, Argo CD Application, Flux HelmRelease, helmfile.yaml) — and a validator that proves the config was materialized and performs.

AICR is not…

Not a distro, not a provisioner or lifecycle manager, not a control plane, not config management. It never runs kubectl apply, never reconciles.

The hook You bring the GPU cluster and your GitOps tooling; AICR emits the config your tools deploy — and can prove it's correct. Its in-cluster footprint is transient: a one-shot snapshot Job, plus short-lived validator Jobs during validate — never a running controller.

Source: ../README.md "What AICR Is Not" · ../docs/contributor/index.md

02 · The model

Four stages, one artifact each

The payoff Same inputs → identical outputs, always. One validated recipe re-renders for whatever pipeline you run.
03 · Architecture

The boundary principle

pkg/cli and pkg/server carry zero business logic — they parse input, format output, map exit codes. Everything real lives in functional packages behind the pkg/client/v1 facade, so CLI and the aicrd REST server share it.

Boundary

pkg/cli · pkg/server → pkg/client/v1

Logic

recipe · collector · validator · bundler

Supply chain

evidence · oci · trust · build

Habit to build When a demo shows a verb, name the package doing the work: recipe→pkg/recipe, validate→pkg/validator, bundle→pkg/bundler. It's the single most enforced rule in review.

Recipes, overlays, mixins → bundles

A query goes in; a resolved, hydrated config comes out. It's a compiler, not a template renderer — and all the config you touch lives in git under recipes/.

A compiler, not templates

06 · The data model

Three layers, all in git

LayerPathRole
Registryrecipes/registry.yamlComponent catalog + single source of truth for versions
Overlaysrecipes/overlays/Criteria-matched recipes; single-parent spec.base
Mixinsrecipes/mixins/constraints + componentRefs only; additive

Decision matrix Change all recipes → registry. Change one shape → overlay. Share across ≥2 leaves → mixin. Merge order: base chain → mixins → profile → registry defaults → CLI --set (later wins).
07 · Inheritance

A real chain: leaves declare only what differs

appliedOverlays
# base → eks → eks-training → gb200-eks-training → gb200-eks-ubuntu-training
$ aicr recipe --service eks --accelerator gb200 --os ubuntu \
      --intent training | yq .metadata.appliedOverlays

Leaf · gb200-eks-ubuntu-training.yaml

componentRefs: [], pulls in the os-ubuntu mixin, adds a K8s ≥ 1.34 constraint. Binds a chain + mixin under one criteria fingerprint.

Intermediate · gb200-eks-training.yaml

Where the GPU-Operator prereqs and the deployment/perf/conformance validation blocks actually live. OS-variant leaves inherit it.

Criteria are not inherited. Mixins carry constraints + componentRefs only. See ../recipes/overlays/, ../recipes/mixins/.

08 · The safety property

Asymmetric matching

Recipe-side any is a wildcard; query-side any is not. A generic query can never silently resolve to a hardware-specific recipe.

generic vs specific
$ aicr recipe --service eks | yq .metadata.appliedOverlays
# → base + eks only. NEVER a GB200/H100-specific leaf.

$ aicr recipe --service eks --accelerator h100 --intent training ...
# → the full, specialized chain merges in.

Specificity() orders the merge; wildcard overlays (e.g. gb200-any.yaml) apply automatically. Source: ../pkg/recipe/criteria.go.

09 · The handoff

Recipe → Bundle: same config, any pipeline

helm default argocd app-of-apps argocd-helm flux HelmRelease helmfile
bundle
$ aicr bundle -r recipe.yaml --deployer helm   -o ./bundles
$ aicr bundle -r recipe.yaml --deployer argocd --repo https://github.com/org/gitops.git -o ./bundles

# overrides: --set (scalar) · --set-json/--set-file (lists+objects) · --dynamic (install-time)
$ aicr bundle -r recipe.yaml --set gpuoperator:driver.version=570.86.16 -o ./bundles

Resolution stops at metadata; per-component values merge at bundle time. "Recipe = what, bundler = how." See ../docs/user/bundling.md.

Module 3

Validation, UAT & the dashboard

One command answers "is this GPU cluster fit to run this workload?" — reproducibly. Its signed result rolls up to a public dashboard anyone can read.

10 · aicr validate

Phases run in a fixed order

ExitMeaning (gate on these)
0pass / skip
2readiness or invalid — fail-closed even with --fail-on-error=false
5timeout (validator section / context deadline)
8phase check failed
11 · Validator surfaces

Four surfaces — picking the wrong one is the #1 wasted PR

1 · Constraint (declarative)

An expression in an overlay validation: block, evaluated against a snapshot value. No code. pkg/constraints

2 · Container check

A Go func run as one K8s Job per check against a live cluster. recipes/validators/catalog.yaml

3 · Component validation

In-process Go run at aicr bundle time — catches misconfig before deploy.

4 · Chainsaw health check

Read-only Chainsaw YAML in recipes/checks/, under a true assert/error allowlist.

Rule of thumb Declarative snapshot assertion → constraint. Active probe of a live cluster → check. The chainsaw allowlist fails closed on every unknown/future op (it runs under cluster-admin). Source: ../docs/contributor/validator.md.
12 · validation.aicr.run

The evidence corroboration dashboard

"How many independent signed parties ran this recipe — and do they agree?" Rebuilt deterministically on every merge; counts distinct verified signers, never re-runs.

StateMeaning
CONFIRMED≥2 distinct signers ran it, all passed — strongest signal
SINGLEexactly 1 signer passed — uncorroborated
CONTESTEDsigners disagree — surfaced first-class, never averaged away
FAILINGevery signer that ran it failed
UNTESTEDno signer ran it — a coverage gap, not a pass
Ground truth The board reads the live data/index.json discovered from GCS evidence coordinates — not the OSS enum — so it can host out-of-enum values. curl | jq it before claiming coverage.
13 · Triage

A red cell: product signal or infra signal?

Product signal

AICR/recipe is actually wrong: a readiness constraint unmet, a check failed on a healthy cluster, a genuine regression (e.g. a released version predating a platform).

Infra signal

The harness/cloud, not the product: bringup terraform failures, stale TF locks / leaked networks, capacity exhaustion, a superseded run, arm64 QEMU-slow builds.

Don't conflate the four surfaces Recipe Health = offline "does it resolve / charts pinned". Coverage Matrix = in-repo CUJ/verb breadth. Evidence Dashboard = live corroboration. TestGrid = the future live board. All anchor on the same coordinate (ADR-012). Tooling: /aicr-uat-report.
Module 4

Supply chain: provenance + evidence

AICR answers two independent trust questions with two separate cryptographic chains. Learn both, and the 4-level trust ladder that gates a deploy.

14 · The mental model

Two proofs

Build provenance

Where did it come from? NVIDIA CI signs images/binaries at release (SLSA, SBOM, cosign keyless). Signer = NVIDIA. Tools = gh attestation verify, cosign.

Recipe evidence

What did validation record? A contributor with cluster access NVIDIA lacks signs an aicr validate result. Signer = the contributor. Tool = aicr evidence verify.

In practice Proof #1 is what you hand downstream to prove NVIDIA built it. Proof #2 is what lets the project accept a recipe PR for GPU hardware no NVIDIA team can reach — without re-running it.
15 · Proof #1

Verify an image — the flag is the L3 check

provenance
# resolve tag → immutable digest, then verify SLSA Build L3 provenance
$ gh attestation verify oci://ghcr.io/nvidia/aicr@$DIGEST --repo NVIDIA/aicr \
      --signer-workflow NVIDIA/aicr/.github/workflows/attest-images.yaml \
      --source-ref refs/tags/$TAG
Why L3 Images are SLSA Build L3 because a reusable workflow is the signing identity — the build job can't forge it. That --signer-workflow pin is the L3 check. Binaries are L2 (signed inline in on-tag.yaml). The SBOM is a different tool (cosign) against a different subject (the per-platform digest, not the index).
16 · Bundle attestation

The 4-level trust ladder

LevelReached when…
verified (4)closed-world inventory + bundle attestation + NVIDIA-CI-pinned binary attestation + no external data
attested (3)signed, but external --data present
unverified (2)valid inventory, but no --attest
unknown (1)a present attestation failed, or a legacy incomplete manifest
gate
$ aicr bundle -r recipe.yaml --attest -o ./bundles
$ aicr verify ./bundles --min-trust-level verified   # default 'max' PASSES an unsigned bundle!

A failed attestation is a hard unknown, not a soft downgrade. demos/bundle-attestation.md

17 · Recipe evidence

The split-leg flow (VPN vs Sigstore egress)

Validation lives on the VPN (where the cluster is); keyless signing needs Fulcio/Rekor, which corporate VPNs routinely block. So split the legs.

split-leg
# LEG 1 — on VPN: validate + emit an UNSIGNED, content-addressed bundle
$ aicr validate -r recipe.yaml -s snapshot.yaml --emit-attestation ./out

# LEG 2 — off VPN: sign (keyless OIDC), push, write the pointer
$ aicr evidence publish ./out --push ghcr.io/<owner>/aicr-evidence
$ aicr evidence verify recipes/evidence/<recipe>/<src>/<digest>.yaml

The bundle is content-addressed → the digest is identical regardless of signing host; only the signature material differs. Community path signs in fork CI (evidence-publish.yaml).

18 · Be honest

What recipe evidence does — and does not — prove

The trust boundary (ADR-007) Recipe evidence is signer-identity-bound, not cluster-physicality-bound. It proves an OIDC identity signed a (recipe, snapshot, results, BOM) tuple — not that the cluster physically existed. It moves the maintainer's question from "did this run?" to "do I trust this signer?"

Where trust actually enters

The merge-time pointer gate is structural (checks the claimed signer's slug + allowlist, no signature check). Cryptographic verification happens after merge at ingest. A lying pointer passes the gate but fails ingest.

The producer side teams forget

Verification proves an artifact you hold is legit — it can't tell you someone signed as you. Keyless leaves no local trace, so AICR signs to Rekor v2 and monitors its own release identity.

Module 5

Dev practices, CI & release

The whole philosophy is "local dev equals CI." One command reproduces the gate; one command family cuts a release with SLSA L3 provenance.

19 · The gate

make qualify = CI, locally

qualify
$ unset GITLAB_TOKEN   # goreleaser fails if it coexists with GITHUB_TOKEN
$ make qualify
# = test-coverage → lint → tuning-check → e2e → scan → license-check
Why it matters When CI is red, the failing job name maps 1:1 to one of these sub-targets — so you know exactly which local command to rerun. Coverage: 80% floor from .settings.yaml; validators/ is deliberately excluded from the profile.

Hardware-free end-to-end: make kwok-e2e RECIPE=eks-training renders + deploys against a simulated cluster.

20 · CI topology

What gates a PR vs what runs on tag

WorkflowRole
qualification.yamlreusable engine: test / lint / cli-e2e / e2e / security-scan
merge-gate.yamlthe PR gate — classifies the diff, runs the suite + CodeQL/malware/actionlint/freshness, funnels into a fail-closed gate job
on-push.yamlruns on main; publishes validator :edge + sha-<commit> images
on-tag.yamlthe release pipeline (candidate → scan → attest → promote)
Fail-closed by design If check-paths errors, downstream jobs skip — so the gate explicitly fails when check-paths didn't succeed. Gate red but every visible job green? Look at check-paths first.
21 · Ship it

PR hygiene & the release runbook

Every commit

git commit -s -S — -s DCO sign-off + -S crypto signature. A branch ruleset rejects unsigned pushes before review. Rebase onto main, squash to one commit, add a theme/* label.

Release = everything on main

make qualify → make bump-patch (tags HEAD, no commit) → on-tag.yaml: candidate images → vuln scan → SLSA L3 attest → promote aliases → GitHub release.

Two docs-hygiene gates AGENTS.md must stay a synced mirror of .claude/CLAUDE.md (check-agents-sync). Any chart/registry change needs make bom-docs committed. Recovery is always "Re-run failed jobs," never manual alias repointing.
